Investigation complete. No files in the repo were changed. Here is what I found and how I would fix it.

What is actually going wrong

Bombadil does not react to anything the page does on its own. The browser only captures a new state after the quiescence timer fires, and that timer is only started after a page load, after an action is applied, or after an uncaught exception. There is no code path anywhere in bombadil-browser that listens for Network.eventSourceMessageReceived, Network.webSocketFrameReceived, Network.dataReceived, or DOM mutations. The only matches for those names in the whole tree are in the generated CDP protocol crate. The top-level run loop in lib/bombadil/src/runner.rs blocks on the next state, steps the verifier with that state's timestamp, picks an action, applies it, and blocks again. So between two actions, the page can receive any number of SSE messages or WebSocket frames and Bombadil sees none of them. It only notices their side effects on the DOM if a later action happens to trigger a capture.

Three consequences follow from that:

- A page with nothing to click is a dead end. In your fixture there are no anchors, buttons, inputs, or ARIA roles, so the action tree is empty and the run aborts with "no actions available". That is exactly how test_sse_message fails with a healthy Chromium. The run lasted under a second and never waited for a message.
- The Wait action cannot be used to wait for a stream. In browser/actions.rs the Wait arm is an empty block. It does nothing and then hands off to the quiescence timer, which fires after the 250ms initial idle window when the page is quiet. waitOnce also refuses to offer another Wait right after a Wait. There is no way to say "sit here for a few seconds and let messages arrive".
- Temporal bounds silently stall. The verifier evaluates eventually(...).within(10, "seconds") only when a state arrives. If no state arrives, the bound is never checked, so the property neither passes nor fails; the run just ends for another reason.

WebSockets are slightly worse than SSE. The activity stream that feeds quiescence only counts requestWillBeSent and responseReceived. An SSE connection produces one of each, so it bumps the timer once and is otherwise invisible. A WebSocket handshake goes through webSocketCreated and friends, so it never bumps the timer at all. Neither blocks quiescence, which is good, but neither can ever cause a capture.

Two things I ruled out. Response interception through the Fetch domain is limited to Script and Document resource types, so the SSE response is never buffered by getResponseBody. And the quiescence per-URL cap means a chatty stream cannot starve the timer.

Your first-run symptom was a red herring. My first run of the SSE test showed Fetch.getResponseBody hanging for five seconds and then the whole CDP session dying. That was not Bombadil. System Chromium 153 on this machine, launched the way chromium.rs launches it, with no URL argument, intermittently never answers on its DevTools port, and the same wedge can hit mid-run. Adding about:blank to the command line made it answer within a second every time. I reran the tests through a wrapper script set via the CHROME env var and the body fetch completed in forty milliseconds. I saved a note about this so it does not bite again. The flake dev shell pins its own Chromium, so you may not see this inside nix develop.

Two small bugs in the work-in-progress test itself, separate from the product issue. The extractor returns a boolean, but the property reads sse_messages.textContent, which is undefined, so it can never be true. Either return the text from the extractor or compare sse_messages.current === true. Also the healthy run showed the extractor already true at the very first snapshot, because the server's throttle emits the first event immediately, so the current fixture does not actually exercise "message arrives later".

Plan to fix and verify

1. Make push-style traffic an activity signal. Enable the relevant CDP events and add Network.eventSourceMessageReceived and Network.webSocketFrameReceived to all_activity in browser/activity.rs, with their own bump duration and their own hit cap so a chatty stream still settles. This makes captures after actions include the latest stream-driven DOM changes rather than racing them.
2. Let the page produce states without an action. Add a new inner event, something like PageActivity, emitted when an SSE message or WebSocket frame arrives while the state machine is Running and no timer is pending. On that event, start a quiescence timer for the current generation so a capture follows once the burst settles. Rate-limit it with a minimum interval between activity-triggered captures so a stream at ten messages per second does not turn into ten captures per second. This is the core fix: SSE and WS updates become observable states the verifier can step on.
3. Give Wait a real duration. Make BrowserAction::Wait carry a duration, sleep for it in apply_action, and only then let quiescence run. Keep a Wait with no duration behaving as today for backward compatibility of recorded action traces. Extend the TypeScript waitOnce generator, or add a wait(ms) helper, so specs can opt in.
4. Stop treating an empty action tree as fatal when time is left. In the browser TestStrategy and the fuzzer, when the tree is empty but the deadline has not passed, return a Wait instead of erroring. Pages that are pure dashboards fed by a stream are legitimate targets and currently cannot be tested at all. Keep the existing no-action-available test passing by making the error only when neither actions nor remaining time exist, or by updating its expectation deliberately.
5. Tests to prove it, in the integration crate:
   - Fix the existing SSE fixture so the first message arrives after a delay of a couple of seconds, so the test genuinely depends on capturing without an action. Property: eventually the list has an item, within a bound.
   - A WebSocket fixture and route in the test server mirroring the SSE one. axum already has a ws feature, so this is a small addition.
   - A negative test: a stream that emits continuously must not prevent quiescence, so captures still happen and the run reaches its time limit rather than the ten-second quiescence cap on every step.
   - A Wait duration test asserting the state timestamp gap matches the requested wait.
   - Keep test_no_action_available and test_disabled_clicks green under whatever rule step 4 settles on.
6. Verify end to end. Run the full integration suite through the CHROME wrapper so Chromium flakiness cannot masquerade as a regression, and run the quiescence and activity unit tests. Then point the CLI at a real SSE or WebSocket application and confirm the trace shows states arriving between actions.
7. Optional but cheap: have chromium.rs pass about:blank as the final argument. It is harmless everywhere and removes the startup wedge seen here.
